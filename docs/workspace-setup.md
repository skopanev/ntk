# Заведение воркспейса и вход участника

Везде ниже `<ws>` — имя воркспейса, `<адрес>` — почта участника.

Всё, кроме входа, выполняется на машине сервиса от администратора: строка подключения лежит в `/etc/ntk/admin.env`.

---

## 1. Схема, роль и права — ОДНОЙ КОМАНДОЙ

```
server/db/bootstrap-workspace.sh <ws>
```

Идемпотентен, можно запускать повторно.

**Не делайте это руками.** Скрипт создаёт не только схему и запись в `core.workspaces`, но и **роль Postgres `ntk_ws_<ws>`**, а на ней держится вся изоляция: вход в воркспейс выполняет `SET LOCAL ROLE`, и без роли любое обращение падает «internal error» — из которого причина никак не следует.

Ровно так и вышло при заведении воркспейса руками: схема была, миграции прошли, справочники засеялись, а роли не было, и воркспейс молча не работал.

Кроме роли скрипт делает три вещи, которые руками забываются:

* **права на БУДУЩИЕ объекты** (`alter default privileges`) — иначе каждая новая таблица из следующей миграции приедет без прав, и выяснится это в бою, а не на миграции;
* `revoke all ... from public` — никаких прав по умолчанию никому;
* `alter role ntk_api noinherit` — **без этого членство в роли даёт права БЕЗ `SET ROLE`, и изоляция превращается в фикцию.** Утверждается при каждом заведении.

Сам `ntk_api` прав на схему не имеет: он лишь член роли и входит через `SET ROLE`. Поэтому забытый фильтр в коде не открывает чужой воркспейс — привилегий просто нет.

## 2. Миграции

```
ntk-migrate
```

Проходит по всем воркспейсам; для существующих это пустая работа — применённое отмечено в `<ws>._migrations`. Новая схема получает таблицы, справочники статусов и приоритетов, пределы записи и политики.

**Сверьте, что бинарь не старее исходников:** SQL подшит в него через `include_str!`, поэтому установленный бинарь применит ровно то, что в нём есть.

```sql
select count(*) from <ws>._migrations;   -- должно совпасть с числом файлов в sql/
```

## 3. Векторизация

```sql
update <ws>.vector_policy set enabled = true;
```

Умолчания нового воркспейса: `stop_on_similar = false`, `min_score = 0.75`. Принудительный поиск дублей при заведении тикета ВЫКЛЮЧЕН — включение векторизации его не включает. Если нужен:

```sql
update <ws>.vector_policy set stop_on_similar = true, min_score = 0.6;
```

Порог без нужды не трогать: правильное число зависит от корпуса, а не от вкуса.

## 4. Проект

Хотя бы один нужен сразу — без него нечего заводить, а проект по упоминанию больше не создаётся:

```
ntk projects --add <проект> -W <ws>
```

## 5. Доступ участника

Строку в `core.users` и членство в `core.user_workspaces` заводить НЕ надо: они создаются при первом входе. Нужно правило зачисления.

**Для почты на публичном домене — правило по АДРЕСУ:**

```sql
insert into core.enrollment_rules (match_type, match_value, workspaces, role)
values ('email','<адрес>','{<ws>}','member');
```

> **Доменное правило для публичного почтовика — дыра, а не настройка.** Оно пустит в воркспейс любого владельца почты на этом домене. Доменные правила — только для доменов, которыми вы владеете.

Правило по адресу сильнее доменного и **снимает отказ для личного аккаунта**: Google отдаёт признак корпоративного домена только рабочим аккаунтам, и личный отвергается на входе — кроме случая, когда администратор выписал этот адрес отдельной строкой.

Идентификатор пользователя берётся из части адреса до `@`. Если запись с таким идентификатором уже есть и на ней ДРУГОЙ адрес, вход отвергается: иначе совпадение инициалов отдало бы человеку чужие тикеты.

Добавить уже существующего пользователя в ещё один воркспейс — строкой:

```sql
insert into core.user_workspaces (user_id, workspace) values ('<id>','<ws>');
```

## 6. Вход участника

```
curl -fsSL <адрес сервиса>/v1/install.sh | sh
ntk login
```

Установщик кладёт бинарь в `/usr/local/bin`; иначе `... | NTK_DIR=~/bin sh`. Скачанное сверяется по sha256 ДО того, как станет исполняемым. `ntk login` печатает адрес и код: открыть, ввести, войти через Google.

## 7. Проверка — обращением, а не чтением

```
ntk whoami                       # воркспейс должен быть в списке
ntk -W <ws> ls                   # не "internal error" — значит роль на месте
ntk -W <ws> create "проба" -P <проект>
ntk -W <ws> rm <id> --yes
ntk -W <чужой> ls                # обязан ответить отказом
```

Первые две строчки важнее прочих: именно они ловят отсутствующую роль, которую SQL-проверки не видят вовсе.

---

## Что не утекает

Список воркспейсов каждому отдаётся только свой: `core.resolve_key` соединяет ключ с `core.user_workspaces` по владельцу, общего списка нет ни в одной ручке наружу.
