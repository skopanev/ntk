# Заведение воркспейса и вход участника

Команды для заведения воркспейса НЕТ: всё делается вручную в базе, и порядок важен. Этот файл — порядок действий, а не рассказ о нём.

Везде ниже `<ws>` — имя воркспейса, `<адрес>` — почта участника.

Всё выполняется на машине сервиса, от администратора: строка подключения лежит в `/etc/ntk/admin.env` (`DATABASE_URL`).

---

## 1. Схема и запись о воркспейсе

Сначала схема, потом запись в справочнике, и только потом объекты. Обратный порядок не работает: `ntk-migrate` берёт список схем из `core.workspaces`, а не выдумывает его — и откажется, если справочник пуст.

```sql
create schema if not exists <ws>;
insert into core.workspaces (name, schema_name) values ('<ws>','<ws>');
```

Имя воркспейса и имя схемы совпадают. Недопустимое имя `ntk-migrate` отвергнет сам.

## 2. Миграции

```
ntk-migrate
```

Проходит по ВСЕМ воркспейсам сразу; для существующих это пустая работа — применённое отмечено в `<ws>._migrations`. Новая схема получает всё с нуля: таблицы, справочники статусов и приоритетов, пределы записи, политики.

**Сверьте, что бинарь не старее исходников.** SQL подшит в него через `include_str!`, поэтому установленный бинарь применит ровно то, что в нём есть:

```sql
select count(*) from <ws>._migrations;   -- должно совпасть с числом файлов в sql/
```

Недостающее применяется руками из соответствующих файлов `sql/`.

## 3. Векторизация

```sql
update <ws>.vector_policy set enabled = true;
```

Умолчания нового воркспейса: `stop_on_similar = false`, `min_score = 0.75`, `block_score = 0.8`. Принудительный поиск дублей при заведении тикета выключен. Если он нужен:

```sql
update <ws>.vector_policy set stop_on_similar = true, min_score = 0.6;
```

Порог трогать без нужды не стоит: правильное число зависит от корпуса, а не от вкуса. Пустому воркспейсу засевать нечего — долг появится с первым тикетом; включение шлёт уведомление, и обработчик подхватывает сам.

## 4. Доступ участника

Строку в `core.users` и членство в `core.user_workspaces` заводить НЕ надо: они создаются при первом входе. Нужно только правило зачисления.

**Для почты на публичном домене — правило по АДРЕСУ:**

```sql
insert into core.enrollment_rules (match_type, match_value, workspaces, role)
values ('email','<адрес>','{<ws>}','member');
```

> **Доменное правило для публичного почтовика — дыра, а не настройка.** `('domain','<публичный почтовик>', …)` пустит в воркспейс ЛЮБОГО владельца почты на этом домене. Доменные правила — только для доменов, которыми вы владеете.

Правило по адресу сильнее доменного: попадая под оба, человек получает адресное.

Идентификатор пользователя берётся из части адреса до `@`. Если запись с таким идентификатором уже есть и на ней ДРУГОЙ адрес, вход отвергается — иначе совпадение инициалов отдало бы человеку чужие тикеты. Разводит такие случаи администратор вручную.

## 5. Вход участника

```
curl -fsSL <адрес сервиса>/v1/install.sh | sh
ntk login
```

Установщик кладёт бинарь в `/usr/local/bin`; иначе `... | NTK_DIR=~/bin sh`. Скачанное сверяется по sha256 ДО того, как станет исполняемым.

`ntk login` печатает адрес и код: открыть адрес, ввести код, войти через Google. Ключ сохраняется в файле настроек сам. Проверка — `ntk whoami`: она должна назвать воркспейс.

## 6. Проверка сделанного

```sql
select count(*) from information_schema.tables where table_schema='<ws>';
select count(*) from <ws>._migrations;
select count(*) from pg_indexes where schemaname='<ws>' and tablename='tickets';
select * from <ws>.vector_policy;
select * from <ws>.write_limits;
select * from core.enrollment_rules where match_value='<адрес>';
```

---

## Что не утекает

Список воркспейсов каждому отдаётся ТОЛЬКО свой: `core.resolve_key` соединяет ключ с `core.user_workspaces` по владельцу, и общего списка нет ни в одной ручке наружу. Единственное чтение `core.workspaces` целиком — фоновый обработчик долга векторизации, он на сервере.

Проверять это стоит не по коду, а обращением: чужой воркспейс не должен появляться в `ntk whoami`, а `ntk -W <чужой> ls` обязан ответить отказом.
