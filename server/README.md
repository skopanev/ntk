# server — дроплет под ntk 0.5.0

Всё, что нужно, чтобы поднять сервер ntk с нуля, и запись того, как он поднят
сейчас. Настроено 2026-09-01.

## Что здесь работает

```
агенты, ноуты юристов
        │  HTTPS 443 + ключ воркспейса
        ▼
     Caddy  ──HTTP localhost:8080──>  ntk-api  ──localhost:5432──>  Postgres
        │                             (crates/ntk-api)
   $DOMAIN → дроплет (адрес и домен — в ops-конфиге, не в репозитории)
```

**Postgres наружу не смотрит.** Единственное, что торчит в интернет — Caddy на 443.
Кредов к базе нет ни на одной клиентской машине: клиент предъявляет ключ воркспейса
API, а с базой разговаривает только API по localhost.

Следствие, ради которого так сделано: сколько бы агентов ни ходило по HTTP, реальных
соединений к Postgres остаётся горстка — пул внутри API. Пулер (PgBouncer) не нужен.

## Сервер

| | |
|---|---|
| IP | в ops-конфиге; скрипты берут из `NTK_HOST` |
| Домен | в ops-конфиге; `provision.sh` подставляет `DOMAIN` в `__DOMAIN__` (A-запись, TTL 300, зона на Google) |
| ОС | Ubuntu 24.04.4 LTS |
| Ресурсы | 1 vCPU, 2 ГБ RAM, 48 ГБ NVMe |
| Postgres | 16.15 |
| Caddy | 2.11.4 |
| Node | **не нужен** — `ntk-api` собирается на Rust, см. `release.sh` |

Тариф 2 ГБ выбран не из-за объёма данных (365 тикетов весят мегабайты), а из-за
того, что на одной коробке живут Postgres, ntk-api и Caddy. На 1 ГБ первый же
`pg_dump` под нагрузкой рискует поймать OOM-killer, а OOM здесь — это вставшая
очередь тикетов у всех агентов сразу.

## Как поднять с нуля

```bash
scp -r server/. root@<ip>:/opt/ntk/server/
ssh root@<ip> 'cd /opt/ntk/server && DOMAIN=<домен> bash provision.sh'
```

`provision.sh` идемпотентен — повторный запуск безопасен. Он делает:

1. Обновляет систему, включает `unattended-upgrades`.
2. Файрвол `ufw`: наружу только 22, 80 (ACME) и 443. **5432 закрыт явным `DENY`.**
3. Ставит Caddy, подставляет домен в `Caddyfile`.
4. Кладёт конфиги Postgres: `listen_addresses = 'localhost'`, `scram-sha-256`,
   тюнинг под 2 ГБ.
5. Создаёт роли `ntk_admin` (миграции, схемы) и `ntk_api` (сервис) и базу `ntk`.
   **Ни одна из ролей не суперпользователь.**

Пароли ролей скрипт не задаёт — это отдельный шаг, см. ниже.

## Секреты

**В репозитории их нет и не будет.** `.gitignore` отсекает `.env`, `.env.*`,
`*.key`, `*.pem`, `*.crt`; `server/.env.example` — единственный шаблон, который
проходит. Проверено `git add -n`: `server/.env` отклоняется, `server/.env.example`
проходит.

Рабочие значения живут на дроплете:

| Файл | Права | Что внутри |
|---|---|---|
| `/etc/ntk/api.env` | `600 root` | `DATABASE_URL` под `ntk_api`, `PORT` |
| `/etc/ntk/admin.env` | `600 root` | `DATABASE_URL` под `ntk_admin` |

Пароли сгенерированы на сервере (`openssl rand`) и наружу не выводились. Сменить:

```bash
sudo -u postgres psql -c "alter role ntk_api with password '<новый>'"
# и поправить /etc/ntk/api.env
```

Второй слой защиты — тест в юните U4, который распаковывает собранный `tgz` и
падает, если внутри есть `.env` или что-то похожее на ключ. `.gitignore` не спасёт
от `git add -f`, а тест смотрит только в пакет: по отдельности не полон ни один.

В публикуемый пакет `server/` не попадёт и так: в `npm-publish/package.json` стоит
`files: ["cli.js", "lib/", "node_modules/"]` — белый список.

## Файлы

| Путь | Назначение |
|---|---|
| `provision.sh` | первичная настройка, идемпотентна |
| `verify.sh` | проверка **снаружи** — запускать не на дроплете |
| `postgres/ntk.conf` | только отличия от умолчаний; `listen_addresses = 'localhost'` |
| `postgres/pg_hba.conf` | только локальные подключения, внешних строк нет |
| `caddy/Caddyfile` | автоматический TLS, реверс-прокси на `localhost:8080` |
| `systemd/ntk-api.service` | юнит сервиса; бинарь кладёт `release.sh` в `/opt/ntk/bin` |
| `systemd/ntk-backup.{service,timer}` | ночной дамп, 03:17 UTC |
| `backup/pg_backup.sh` | `pg_dump` custom-формата в Spaces через curl `--aws-sigv4` |
| `backup/restore-verify.sh` | разворачивает последний дамп и проверяет данные |

## Бэкапы — включены и проверены

Ночной `pg_dump` в Spaces, таймер `ntk-backup.timer`, 03:17 UTC с разбросом до
10 минут. Бакет `ntk-storage`, регион `ams3`.

Загрузка идёт **обычным curl**: он умеет подписывать S3-запросы сам
(`--aws-sigv4`, начиная с 7.75), на сервере curl 8.5. Отдельный S3-клиент не
ставится осознанно — `awscli` притащил бы Python с boto3 ради одного PUT, да и
из репозиториев Ubuntu 24.04 он убран (`no installation candidate`).

Каждый прогон кладёт два объекта: `postgres/ntk-<timestamp>.dump` для истории и
`postgres/latest.dump` как указатель. Указатель нужен, чтобы `restore-verify.sh`
не разбирал XML листинга ради поиска свежего файла.

**Непроверенный бэкап бэкапом не считается.** `restore-verify.sh` скачивает
`latest.dump`, разворачивает в одноразовую базу, прогоняет `pg_restore` и
сообщает число схем воркспейсов. Проверено 2026-09-01: дамп ушёл, скачался,
восстановился.

Ротацию старых объектов делает **lifecycle-правило бакета**, а не скрипт:
удалять чужие объекты из cron — лишний риск. Локально дампы живут неделю.

## Проверка

Снаружи, не с дроплета:

```bash
./verify.sh "$DOMAIN"
```

Состояние на 2026-09-01, проверено фактически, а не по конфигу:

| Проверка | Результат |
|---|---|
| 22 снаружи | открыт |
| 80 снаружи | открыт (ACME) |
| 443 снаружи | открыт |
| **5432 снаружи** | **закрыт** |
| Postgres слушает | только `127.0.0.1:5432` и `[::1]:5432` |
| TLS | сертификат Let's Encrypt на `$DOMAIN`, проверка проходит (`ssl_verify_result: 0`), действует до 30.11.2026 |
| `ntk_api` подключается | да |
| `ntk_api` суперпользователь | нет (`rolsuper = f`) |
| `HTTP 502` на `https://$DOMAIN/` | сервис не запущен: `systemctl status ntk-api` |
| Бэкап в Spaces | дамп загружен, скачан и восстановлен |
| `ntk-backup.timer` | активен, следующий прогон 03:17 UTC |

## Порядок развёртывания

Схема `core` заводится ПЕРВОЙ и вручную — миграции в `sql/` создают в ней
таблицы (`core.oauth_clients`, `core.releases`), но саму схему не создают:

```bash
psql "$DATABASE_URL" -f server/db/core.sql     # схема core: люди, ключи, воркспейсы
cargo run --bin ntk-migrate                    # sql/ — объекты воркспейсов
```

Дальше сервис выкатывает `release.sh` из корня репозитория: он собирает бинарь
на дроплете, кладёт его в `/opt/ntk/bin` и перезапускает `ntk-api.service`.
